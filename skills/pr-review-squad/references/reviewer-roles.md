# 리뷰어와 검증자 역할 지시

## 공통 규칙 (모든 리뷰어)

- 자기 관점 밖의 문제는 적지 않는다. 다른 리뷰어가 본다.
- 모든 지적에는 `file`, `line`, 코드 인용(`evidence`)이 있어야 한다. 인용할 수 없으면 지적하지 않는다.
- 모든 지적에는 `scenario`(어떤 상황에서 어떤 문제가 생기는지)와 `suggestion`(어떻게 고치면 좋은지)도 필요하다. 참고 사항(C2)도 예외가 아니며 한두 문장이면 된다. `title`과 `scenario`는 개발자가 아닌 사람도 읽을 수 있게 쓴다.
- 변경된 줄과 그 주변(호출하는 쪽, 호출되는 쪽 한 단계)만 본다.
- 반환 형식은 [output-template.md](output-template.md)의 findings JSON 배열 하나뿐이다. 설명 문장을 덧붙이지 않는다.
- 문제가 없으면 빈 배열 `[]`을 반환한다. 억지로 찾지 않는다.

## 1. 정확성 리뷰어 (`correctness`)

PR이 말하는 의도대로 동작하는지 본다.

- 조건문, 경계값(0, 빈 값, 최대값), off-by-one, null/None 처리
- 오류 처리: 예외가 삼켜지는지, 실패 시 상태가 반쯤 바뀐 채 남는지
- 동시성, 순서 가정, 재시도 시 중복 실행
- 시그니처나 반환 형식이 바뀌었는데 호출하는 쪽이 따라오지 않았는지
- PR 설명과 코드가 다르게 동작하는지

### 의도 대조 절차 (PR 본문이 있을 때 필수)

PR 본문에 규칙, 동작표, 시나리오 목록이 있으면 diff를 훑는 것으로 끝내지 말고 항목별로 대조한다.

1. 본문에서 검증 가능한 주장을 뽑는다. 예: "미지정이면 기존 값 유지", "Local이면 NULL", "잘못된 형식은 거부".
2. 주장마다 그것을 구현한 코드 위치를 찾고, 입력 → 결과를 한 줄로 따라가 본다. 찾지 못하면 그 자체가 지적이다.
3. 한 주장이 여러 경로(단건, 다건, patch, 저장 전/후)에 걸쳐 있으면 경로마다 같은 결과가 나오는지 본다. 경로마다 규칙이 다르게 구현된 곳이 버그가 가장 잘 나오는 곳이다.
4. 읽기와 쓰기 사이에 틈이 있는지 본다(조회 후 갱신, 캐시, 재시도).

지적이 없을 때도 위 절차를 거친 뒤에 `[]`을 반환한다. 대조 없이 diff만 훑고 `[]`을 반환하면 안 된다.

## 2. 보안 리뷰어 (`security`)

- 입력 검증 누락, SQL/명령어/경로 주입, XSS
- 인증과 권한 확인이 빠진 경로
- 비밀 값 하드코딩, 로그에 민감 정보 출력
- 안전하지 않은 역직렬화, 임의 파일 접근
- 새로 추가된 의존성의 알려진 위험 (확인 가능한 경우만)

비밀 값을 발견하면 `evidence`에 값을 적지 않고 `"[REDACTED]"`로 대체한다.

## 3. 가독성·유지보수 리뷰어 (`maintainability`)

- 함수가 너무 길거나 한 가지 이상의 일을 하는지
- 이름이 동작을 설명하는지, 중복 코드가 있는지
- 기존 코드 스타일과 팀 규칙(`CONVENTIONS.md` 등)을 따르는지
- 주석이 코드와 어긋나는지, 죽은 코드가 남았는지

이 관점의 지적은 대부분 C2다. 구조 문제 때문에 버그가 날 것이 분명한 경우에만 C1로 올린다.

## 4. 테스트 리뷰어 (`testing`)

- 새 로직과 버그 수정에 대응하는 테스트가 있는지
- 테스트가 구현을 그대로 베낀 것은 아닌지 (구현에서 기대값을 계산하면 독립된 기준이 못 된다)
- 경계값, 실패 경로가 테스트되는지
- 기존 테스트가 PR로 깨지는지 (실행 가능하면 실행해서 결과를 근거로 쓴다)
- 테스트를 약하게 고쳐서 통과시킨 흔적이 있는지

테스트가 없다는 이유만으로 C0은 되지 않는다. C1은 [rubric.md](rubric.md)의 "테스트 부재 지적의 등급" 세 조건(PR이 바꾼 분기, 회귀 시 되돌리기 어려운 결과, 다른 안전망 없음)을 모두 만족할 때만이다. 하나라도 빠지면 C2다.

조건 (c)(다른 안전망이 있다)를 이유로 C1이 될 수 있는 지적을 C2로 낮출 때는 `scenario`에 안전망으로 본 테스트의 `파일:줄`과 함수 이름, 그리고 그 테스트가 어떤 분기를 단언하는지 한 줄로 적는다. C2는 검증자가 확인하지 않으므로, 종합자가 이 기록으로 하향 근거를 확인한다. 이름만 적고 경로를 적지 못하면 낮추지 않는다.

구현의 결함(예: 서버가 입력을 검증하지 않는다)을 발견했더라도 테스트 지적에 섞지 않는다. 그 결함은 정확성/보안 리뷰어의 몫이므로, 테스트 지적에는 "이 동작을 검증하는 테스트가 없다"만 쓴다.

"테스트가 없다"고 지적하기 전에 PR이 바꾸지 않은 기존 테스트 디렉터리(`tests/` 전체)에서 같은 동작을 이미 다루는지 먼저 찾는다. PR diff에 테스트가 없다는 것과 저장소에 테스트가 없다는 것은 다르다.

테스트를 실행하지 못한 것은 한계이지 지적이 아니다. 지적으로 만들지 않고 보고서의 "보지 못한 것"에만 남긴다.

## 검증자 (`verifier`)

검증자는 지적 한 건과 해당 코드 위치만 받는다. 리뷰어의 확신 정도나 다른 지적은 모른다.

해야 할 일:

1. `evidence`가 실제 코드와 일치하는지 파일을 직접 열어 확인한다.
2. 지적이 틀렸다는 근거를 적극적으로 찾는다. 다른 곳에서 이미 방어하고 있는지, 호출 경로상 그 입력이 들어올 수 없는지, 테스트가 이미 커버하는지.
3. 가능하면 재현한다. 짧은 스크립트나 기존 테스트 실행으로 확인한다. 위험한 명령, 설치, 네트워크 호출은 하지 않는다.
4. 판정을 내린다.
   - `CONFIRMED`: 반박 근거를 찾지 못했고 지적이 코드로 확인된다.
   - `REJECTED`: 반박 근거가 있다. 근거를 한 문장으로 적는다.
   - `UNCERTAIN`: 코드만으로 판단할 수 없다. 무엇이 있으면 판단 가능한지 적는다.

검증자는 등급을 바꾸지 않는다. 등급 조정은 종합자가 한다.

### 테스트 부재 지적을 검증할 때

"테스트가 없다"는 지적은 다음을 모두 확인한 뒤에만 `CONFIRMED`로 한다.

- PR이 바꾼 테스트 파일뿐 아니라 저장소의 기존 테스트 트리 전체를 파일 목록(`git/trees?recursive=1`)으로 훑고, 관련 키워드(함수명, 필드명, 시나리오 이름)로 찾았다.
- 기존 테스트가 해당 함수를 호출해도 해당 필드를 단언하지 않거나, 함수를 mock하거나, 다른 코드가 결과를 덮어쓰면 "다루지 않는다"로 본다.

### 호출 경로 추적 규칙 (필수)

"기존 테스트가 이 분기를 다루지 못한다"는 판단은 다음 이유 중 하나로 내리는 경우가 많고, 이유를 코드로 따라가 보지 않으면 틀리기 쉽다.

- "다른 코드가 결과를 덮어쓴다"
- "함수를 mock해서 실제 분기에 도달하지 않는다"
- "다른 경로(단건/다건/patch)의 테스트라서 해당하지 않는다"

이런 이유로 `CONFIRMED`하려면 검증자는 **의심스러운 테스트마다** 호출 경로를 끝까지 따라가 `trace`에 적어야 한다.

```
테스트 파일:줄 → 호출하는 함수 파일:줄 → ... → 지적이 말하는 분기 파일:줄 → 결과가 쓰이는 곳 파일:줄
```

- 경로가 지적된 분기에 **도달하지 못하는 지점**(실제로 mock되는 줄, 덮어쓰는 줄)을 줄 번호로 짚을 수 있으면 `CONFIRMED`.
- 경로가 분기에 **도달하고 결과를 단언**하면 그 부분은 이미 다뤄진 것이다. 지적 전체를 `REJECTED`하거나, 남은 공백만 `verdict_reason`에 적는다.
- 같은 함수가 **다른 경로에서도 호출**되는지 호출하는 쪽을 검색(`grep`)해서 확인한다. 테스트 이름이나 파일명("batch", "common_form")만 보고 해당 없다고 판단하지 않는다.
- 줄 번호로 경로를 적지 못하면 `UNCERTAIN`으로 하고, 어떤 파일을 더 읽어야 하는지 적는다. 추측으로 `CONFIRMED`하지 않는다.

### 일부만 맞는 지적

지적의 핵심 주장이 틀렸고 부수적인 일부만 맞으면 `REJECTED`로 하되 `verdict_reason`에 맞는 부분을 한 문장으로 적는다. 종합자는 맞는 부분을 C2 새 지적으로 다시 쓸지 결정한다. 핵심 주장이 맞고 범위만 과장됐으면 `CONFIRMED`로 하고 `verdict_reason`에 과장된 부분을 적는다.
