# 출력 형식

## findings JSON (리뷰어, 검증자, 종합자가 사용)

배열 하나. 지적 한 건의 필드는 다음과 같다.

```json
[
  {
    "id": "F1",
    "perspective": "correctness",
    "severity": "C0",
    "file": "src/payment.py",
    "line": 42,
    "title": "할인율이 100%일 때 0으로 나눈다",
    "evidence": "total = price / (1 - discount)",
    "scenario": "discount=1.0 이면 ZeroDivisionError로 결제 요청이 500을 반환한다",
    "suggestion": "discount가 1 이상이면 입력 단계에서 거부한다",
    "verdict": "CONFIRMED",
    "verdict_reason": "호출 경로상 discount 상한 검사가 없고, 테스트도 해당 값을 다루지 않는다"
  }
]
```

| 필드 | 필수 | 규칙 |
|---|---|---|
| `id` | O | 중복 없는 문자열 |
| `perspective` | O | `correctness`, `security`, `maintainability`, `testing` 중 하나 |
| `severity` | O | `C0`, `C1`, `C2` 중 하나. 내부 코드이며 사용자에게는 아래 표의 이름으로 보인다 |
| `file` | O | 저장소 기준 상대 경로 |
| `line` | O | 1 이상의 정수 |
| `title` | O | 한 문장. 보고서의 소제목이 되므로 개발자가 아니어도 이해할 수 있게 쓴다 |
| `evidence` | O | 코드 인용 또는 실행 결과. 비어 있으면 안 된다. 비밀 값은 `[REDACTED]` |
| `scenario` | **모든 지적 O** | 어떤 상황에서 어떤 문제가 생기는지. 보고서의 "어떤 상황에서 문제가 되나요?"에 그대로 나온다. 참고 사항(C2)은 한두 문장이면 된다 |
| `suggestion` | O | 수정 방향. 코드를 직접 고치지 않는다 |
| `verdict` | O (종합 단계) | `CONFIRMED`, `REJECTED`, `UNCERTAIN`. C2는 검증하지 않으므로 `NOT_VERIFIED` |
| `verdict_reason` | O (종합 단계) | 한 문장 |
| `also_reported_by` | 선택 | 같은 문제를 지적한 **다른** 관점 이름의 배열(병합한 경우). 보고서에 "같은 문제를 ○○ 관점의 리뷰어도 지적했습니다"로 나온다. 제목에 병합 메모를 적지 않는다 |
| `trace` | 테스트 지적의 C0/C1 `CONFIRMED`는 O | 검증자가 따라간 호출 경로. 문자열 배열, 각 항목은 `테스트:줄 → 호출 함수:줄 → ... → 지적된 분기:줄` 형태. 다른 지적은 생략 가능 |

리뷰어 단계에서는 `verdict`, `verdict_reason`을 비워 둔다. 검증자와 종합자가 채운다.

## 사용자에게 보이는 이름

보고서에는 내부 코드(C0/C1/C2)를 쓰지 않는다. `scripts/render_report.py`가 아래 이름으로 바꿔 출력한다.

| 내부 코드 | 보고서에서 | 뜻 |
|---|---|---|
| C0 | 🔴 머지 전에 꼭 고쳐야 할 문제 | 잘못된 결과, 데이터 손실, 보안 취약점, 크래시 |
| C1 | 🟠 고치는 것을 권장 | 지금은 안 터져도 곧 문제가 될 것 |
| C2 | 🟡 참고·제안 | 이름, 중복, 구조 등 판정에 영향 없는 제안 |

| 판정 | 보고서 제목 |
|---|---|
| `REQUEST_CHANGES` | ⛔ 머지 전에 수정이 필요합니다 |
| `COMMENT` | 💬 수정을 권장하는 사항이 있습니다 |
| `APPROVE` | ✅ 확인된 문제가 없습니다 |

## 보고서

보고서는 직접 쓰지 않고 스크립트로 만든다. 표현이 실행마다 달라지는 것을 막고, GitHub 마크다운으로 바로 붙일 수 있게 하기 위해서다.

```bash
python3 scripts/render_report.py findings.json \
  --not-reviewed "테스트와 린터는 실행하지 못했습니다" \
  --not-reviewed "diff 밖 파일은 변경 지점의 호출 관계만 한 단계 확인했습니다" > review.md
```

보고서는 이 순서를 따른다.

1. 제목: 판정 아이콘과 한 줄 설명, AI가 작성했고 사람의 리뷰를 대체하지 않는다는 안내
2. 요약 한 줄(꼭 고쳐야 할 문제 / 권장 / 참고 / 확인 필요 건수, 반려된 지적 수)과 관점별 점수 표
3. 🔴, 🟠, 🟡 섹션. **모든 지적을 펼친다.** 지적마다 다음을 모두 보여 준다.
   - 제목, `파일:줄`, 관점, 지적 번호
   - 근거 코드
   - 어떤 상황에서 문제가 되나요? (`scenario`)
   - 어떻게 고치면 좋을까요? (`suggestion`)
   - 검증 결과 한 줄 (확인됨 / 판단 보류 / 참고 사항이라 검증 안 함). 호출 경로(`trace`)가 있으면 접어서 보여 준다
4. ❓ 확인이 필요한 항목 (`UNCERTAIN`. 건수와 판정에는 넣지 않는다)
5. 이번 리뷰가 확인하지 못한 것 (`--not-reviewed`로 준 항목. 없으면 "별도로 기록된 항목이 없습니다")

규칙:
- 판정과 점수는 스크립트가 계산한 값이다. 손으로 고치지 않는다.
- 지적이 없는 섹션도 생략하지 않고 "없음"으로 둔다.
- 형식 오류가 있으면 스크립트가 보고서를 만들지 않는다. `findings.json`을 고친 뒤 다시 실행한다.
- 보고서가 GitHub 댓글 한도(65,536자)에 가까우면 스크립트가 경고한다. 그때는 여러 댓글로 나눈다.
