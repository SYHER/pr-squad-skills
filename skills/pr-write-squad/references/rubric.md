# 평가 기준

PR 설명이 좋은지는 **읽는 사람이 코드를 열기 전에 알아야 하는 것을 알려 주는가**로 정한다. 길이나 문장 솜씨는 기준이 아니다.

## 여섯 가지 기준

| # | 기준 | 통과 조건 | 흔한 실패 |
|---|---|---|---|
| R1 | 무엇을 바꿨나 | 동작이 어떻게 달라지는지 한두 문장으로 쓴다 | 파일 이름만 나열, "여러 가지 개선" |
| R2 | 왜 바꿨나 | 이슈, 버그, 요구 중 하나가 드러난다. 모르면 모른다고 쓰고 물어본다 | 이유를 지어냄, 이유 누락 |
| R3 | 어떻게 확인했나 | 실제 실행한 명령과 결과만 쓴다. 실행하지 못한 것은 이유와 함께 쓴다 | 안 돌린 테스트를 "통과", "확인했습니다"만 씀 |
| R4 | 이번에 하지 않은 것 | 일부러 뺀 것, 후속 작업을 쓴다. 없으면 "없음" | 범위가 모호해 리뷰어가 추측 |
| R5 | 위험과 되돌리는 방법 | 영향받는 동작과 되돌리는 법을 쓴다. 마이그레이션, 설정, 공개 인터페이스 변경은 필수 | "영향 없음"이라고만 씀 |
| R6 | 먼저 볼 곳 (선택) | 핵심 파일이나 함수를 한두 개 짚는다 | 큰 PR인데 안내 없음 |

R1~R5는 필수이고 R6은 변경이 크거나 여러 파일에 걸칠 때 권한다.

## 통과 조건 (모두 만족, 점수로 상쇄하지 않음)

1. `validate_pr.py` 오류 0건.
2. 사실 확인에서 `UNSUPPORTED`와 `UNCERTAIN`이 0건.
3. 처음 읽는 리뷰어가 다섯 질문 모두 "알 수 없음" 없이 답함.

## `validate_pr.py`가 결정적으로 막는 것

| 코드 | 막는 것 |
|---|---|
| `TITLE_*` | 제목이 비었거나 72자 초과, 마침표로 끝남, 저장소가 정한 형식(`--title-pattern`)과 다름, 자리표시자 |
| `BODY_EMPTY`, `BODY_TOO_LONG` | 본문이 비었거나 GitHub 한도(65,536자) 초과 |
| `PLACEHOLDER` | 템플릿 안내 주석, `TODO`, `TBD`, `{{...}}`, "여기에 작성" 같은 자리표시자가 남음 |
| `TEMPLATE_SECTION` | 저장소 템플릿의 섹션이 빠졌거나 내용이 비어 있음 (제목에 `(선택)`/`(optional)`이 있으면 면제) |
| `CLAIM_NOT_SUPPORTED` | 사실 확인이 `SUPPORTED`가 아니거나 근거(`파일:줄`)가 없는 주장 |
| `VERIFICATION_*` | `passed`인데 명령이나 출력이 없음, `not_run`인데 이유가 없음, `failed`인데 출력이 없음 |
| `UNBACKED_PASS_CLAIM` | 본문에 "통과" 같은 표현이 있는데 실제로 통과한 검증 기록이 없음 |
| `NOT_RUN_UNMENTIONED` | 실행하지 못한 검증이 있는데 본문이 그 사실을 말하지 않음 |
| `SECRET` | 키, 토큰, 비밀번호처럼 보이는 문자열 |

경고(`warnings`)는 막지는 않지만 읽는 사람이 놓치기 쉬운 것이다: 이유 섹션이나 범위 섹션이 안 보임(템플릿이 없을 때만), 본문이 너무 짧음, 검증 섹션 없음, 선택 목록에 체크한 항목이 하나도 없음, 근거를 확인할 수 없는 체크리스트 항목을 체크함, 본문에 "알 수 없습니다"처럼 모르는 정보를 인정하는 문장이 있음(`UNKNOWN_INFO`: 작성자가 모르면 지어내지 말고 사용자에게 물어 채우거나 지운다).

## 처음 읽는 리뷰어의 다섯 질문

1. 이 PR은 무엇을 바꾸는가?
2. 왜 바꾸는가?
3. 어떻게 확인했는가? 확인하지 못한 것은 무엇인가?
4. 이 PR이 바꾸지 않는 것은 무엇인가?
5. 코드에서 어디를 먼저 봐야 하는가?
